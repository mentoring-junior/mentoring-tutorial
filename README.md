# Mini Sound App — Flutter 온보딩 과제

formebuds2의 **음원 목록 화면**을 아주 작게 줄인 연습용 앱입니다.
BLE, 네이티브 코드, 서버 같은 건 전혀 없고, 로컬 JSON 파일 하나로 시작합니다.

목표는 "모든 걸 아는 것"이 아니라, **우리 앱이 어떤 구조로 돌아가는지 직접 손으로 한 번 짜보는 것**이에요.
과제를 다 끝내고 formebuds2 코드를 열어 보면 "아, 이거 내가 해본 거네" 싶은 부분이 꽤 많을 거예요.

---

## 우리 앱의 지도

처음 보는 단어가 나오면, 일단 **아래 4칸 중 어디에 속하는지**만 먼저 정해 보세요.
나머지는 천천히 알아가도 괜찮아요.

```
 ① 화면(Widget)  →  ② ViewModel  →  ③ Repository  →  ④ 패키지 / 네이티브
 "무엇을 보여줄까"   "상태를 들고 있음"   "데이터를 가져옴"    BLE, 오디오, 플랫폼 채널 …
```

- 이 과제에서는 ①②③을 직접 만들어 봅니다.
- ④는 실제 업무에서 하나씩 만나면서 배워도 충분해요.

## 진행 방법 (과제 1개 기준)

> 📘 처음 하는 거라면 **[PR 가이드](docs/PR_GUIDE.md)** 를 옆에 띄워 두고 따라 해 보세요.
> 처음 한 번 하는 준비(로그인 등), 화면 클릭 순서, 문제가 생겼을 때 해결 방법까지 자세히 적어 뒀어요.
> 아래는 그 요약이에요.

```
main ──●────────────────────●──────────────────●──→
        \                  ↑ 멘토가 머지         \
         task/01 ─●─●─●─●──┘                     task/02 ─●─●─ …
                  작업  리뷰 반영                  (합쳐진 main에서 새로 출발)
```

### ① 최신 main에서 브랜치 만들기

```bash
git switch main
git pull                            # 직전 과제가 합쳐진 최신 main 받기
git switch -c task/01-show-list     # 이번 과제용 브랜치
```

**꼭 `git pull` 먼저!** 과제 3은 과제 2에서 만든 코드를 고치는 작업이라, 옛날 main에서 출발하면 이전 과제 내용이 빠져 있어요.

브랜치 이름은 `task/번호-짧은설명` 으로 맞춰요: `task/00-first-pr`, `task/02-freezed-model` …

### ② 작업하고 커밋 · push

```bash
flutter analyze                     # 문제 없는지 먼저 확인
git add .
git commit -m "과제01: JSON 읽어서 목록 표시"
git push -u origin task/01-show-list   # 처음 한 번만 -u, 이후엔 git push
```

커밋은 **작게 여러 번** 해도 괜찮아요. 머지할 때 하나로 묶여요.

### ③ PR 만들기

- GitHub에서 `task/01-show-list` → `main` 으로 PR을 만들어요.
- PR 양식을 채우고, **멘토를 리뷰어로 지정**해요.

### ④ 리뷰 반영

- 수정 요청을 받으면 **같은 브랜치에서** 고치고 `git push` 하면 돼요.
- PR을 새로 만들 필요 없어요. **기존 PR에 자동으로 반영돼요.**
- 코멘트에 답을 달아 주세요. "반영했어요", "이렇게 이해했는데 맞나요?" 처럼요.

### ⑤ "이 코드 설명해줘" 10분

머지 전에 내가 짠 코드를 멘토에게 말로 설명해요. 말로 설명할 수 있으면 진짜 이해한 거예요.

### ⑥ 머지 → 다음 과제

- 승인되면 **멘토가 main에 머지**해요 (Squash and merge — 과제당 커밋 1개로 묶여요).
- 그다음 다시 ①부터 시작해요.

### 이럴 땐 이렇게

| 상황 | 방법 |
|---|---|
| 리뷰를 기다리는 중이에요 | 다음 과제는 **아직 시작하지 않아요.** 대신 다음 과제 문서를 읽고 키워드를 미리 찾아봐요 |
| `git pull`을 잊고 브랜치를 만들었어요 | 당황하지 말고 멘토에게 알려 주세요. 같이 `git merge main`으로 맞춰 봐요 (좋은 연습이에요) |
| main에서 작업했어요 / main에 push하려고 해요 | **main에는 직접 push하지 않아요.** 멈추고 [PR 가이드의 문제 해결](docs/PR_GUIDE.md#문제가-생겼을-때)을 보거나 멘토에게 알려 주세요 |

## 과제를 푸는 방식

과제에는 **정답 코드가 없어요.** 키워드를 보고 직접 조사해서 적용하는 게 이 과제의 핵심이에요.
그렇다고 혼자 오래 버티라는 뜻은 아니에요.

### 조사 → 작게 실험 → 적용

1. **키워드 조사** — 과제 문서의 "배경 키워드"를 공식 문서에서 찾아봐요.
2. **작게 실험** — 바로 과제에 넣지 말고, 예제를 그대로 따라 쳐서 돌아가는 걸 먼저 봐요.
3. **과제에 적용** — 실험한 걸 내 코드에 맞게 바꿔요.

### 시간 정하기

| 막힌 시간 | 할 일 |
|---|---|
| 15분 | 과제 문서의 **힌트**를 펼쳐 봐요 |
| 30분 | **멘토에게 물어봐요.** 오래 혼자 버틴다고 실력이 느는 게 아니에요 |

### 어디서 찾나요

| 주제 | 문서 |
|---|---|
| Dart 문법 | https://dart.dev/language |
| Flutter 위젯 | https://docs.flutter.dev/ui |
| Riverpod | https://riverpod.dev |
| freezed | https://pub.dev/packages/freezed |
| json_serializable | https://pub.dev/packages/json_serializable |

### ⚠️ 버전을 꼭 확인하세요

검색해서 나온 예제를 **똑같이 따라 했는데 안 되는 이유**의 대부분은 버전 차이예요.

| 패키지 | 우리 버전 | 검색하면 자주 나오는 다른 버전 |
|---|---|---|
| flutter_riverpod | **2.6** | 3.x 예제, `@riverpod` 어노테이션(코드 생성) 방식 → **이 과제에선 안 써요** |
| freezed | **3.x** | 2.x 예제는 `abstract class` / `sealed class`가 빠져 있어요 |

- 우리 버전은 `pubspec.yaml`에서 확인할 수 있어요.
- pub.dev 패키지 페이지의 **Changelog** 탭에서 버전별로 무엇이 바뀌었는지 볼 수 있어요.
- 블로그 글은 **작성 날짜**를 먼저 보세요.

PR의 "AI에게 물어본 것 / 스스로 해결한 것"에 **어디서 찾았는지(링크)** 도 같이 적어 주면 좋아요.

## AI 사용 규칙

AI를 쓰지 말라는 게 아니라, **용도를 나눠서** 쓰자는 거예요.

| ✅ 써도 돼요 | ❌ 과제 중에는 참아요 |
|---|---|
| "`late`가 뭐야?" 같은 개념 질문 | "이 기능 만들어줘" |
| 에러 메시지 해석 | 과제 설명을 통째로 붙여 넣기 |
| **내가 다 짠 코드**를 리뷰받기 | 내가 이해 못 한 코드를 그대로 붙이기 |

PR에 **"AI에게 물어본 것 / 스스로 해결한 것"**을 꼭 적어 주세요.
나중에 돌아보면 내가 생각보다 많이 배웠다는 게 보여요.

## 막혔을 때 순서

1. **에러 메시지를 끝까지 읽기.** 대부분 몇 번째 줄에서 무엇이 문제인지 알려줘요.
2. **정의로 이동하기** (Cmd+클릭). Flutter 위젯도 결국 다트 코드라서 열어 볼 수 있어요.
3. **버전 확인하기.** 따라 한 예제가 우리 패키지 버전과 맞나요? (위의 ⚠️ 표)
4. 15분 막히면 과제 문서의 **힌트**를 펼쳐 보기.
5. **30분 막히면 물어보기.** 질문할 때는 "무엇을 하려고 했고 → 무엇을 해봤고 → 무엇이 안 되는지"를 같이 말해 주세요.

> 모르는 게 나오는 건 당연해요. 선배도 매일 모르는 걸 찾아봅니다.
> 중요한 건 다 아는 게 아니라, **모를 때 어떻게 찾아가는지** 아는 거예요.

## 폴더 구조 (최종 모습)

formebuds2와 비슷한 구조로 맞춰 두었어요.

```
lib/
├── main.dart
├── shared/                      # 여러 화면이 같이 쓰는 것
│   ├── models/sound.dart        # 과제 1~2
│   └── sound_repository.dart    # 과제 3
└── presentation/                # 화면별 폴더
    ├── sound_list/
    │   ├── sound_list_page.dart
    │   └── sound_list_viewmodel.dart   # 과제 3
    ├── sound_detail/            # 과제 4
    └── favorite/                # 과제 4
```

## 자주 쓰는 명령어

```bash
flutter run                          # 실행 (실행 중에 r = hot reload, R = hot restart)
flutter analyze                      # 린트/타입 검사 — PR 전에 꼭 돌리기
dart format lib                      # 코드 정리
dart run build_runner build -d       # freezed / json 코드 생성 (과제 2부터)
flutter test                         # 테스트 (과제 6)
```
